> 状态：设计定稿随实现收口。前置：v1.22.0 已发版（连接器扩展包②③）。
> 关联文档：`OpenForge-B2事件总线设计.md`（notify 预留消费组）、`OpenForge-架构文档.md`（notify"规划未建"）、`OpenForge-多轮测试方案-十至十六轮.md`（测试轮次范式）。

## 0. 背景与范围

v1.22 收口后路线图进入功能补充批次，本批交付三个模块（MVP 边界明确）：

| 模块 | 现状（设计前盘点） | 本批交付 |
|---|---|---|
| 站内通知中心 | **未实现**。事件基建全有：RocketMQ + outbox + 幂等消费（`openforge-common/event`），B2 设计为 notify 预留消费组 | 通知中心落在 **auth 服务**（平台级用户域设施，零新增服务/容器），双通道摄取 + 收件箱 API + 前端铃铛/页面 |
| 审批委托 | **完全不存在**。工作流审批人模型仅 USER/ROLE/USERS | `workflow_delegate` 规则表 + 查询期虚拟收件箱 + 代办办理 + 委托管理页 |
| 回收站 | 无统一回收站。软删除基建已有：9 实体 `deleted` 列 + `@TableLogic`，删除即逻辑删，无查询/恢复入口 | 覆盖 part/bom/doc/drawing 四域：回收站列表 + 恢复 + 前端聚合页 |

**明确不做（P2 记录）**：回收站"彻底删除"（需 MinIO 文件 GC 方案，本期只恢复不销毁，软删行存量即现状）；doc/drawing 之外的域（project/knowledge/change/metadata 动态表无 deleted 列）；通知的已读保留期清理策略；材料/文档/图纸发布类事件的订阅式通知（payload 无收件人语义，需订阅模型，见 §1.5）。

## 1. 站内通知中心（auth 服务内嵌）

### 1.1 落点决策

**auth 内嵌而非新建 notify 服务**：宿主机 16GB 且 docker 审计刚从 12.7GB→1.8GB 收缩足迹，新增第 12 个常驻服务违背方向；通知是平台级用户域设施，auth 已托管平台共享事件表（V23 `sys_event_outbox/sys_event_consumed` 在 auth 迁移命名空间），有先例。RocketMQ client 经 openforge-common 传递，auth 零新增依赖。消费者启动失败仅 ERROR 日志不阻断 auth 启动（对齐 connector 消费者容错语义）。

### 1.2 数据模型（auth V31__notify_message.sql）

```sql
CREATE TABLE notify_message (
    id          BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    tenant_id   BIGINT       NOT NULL DEFAULT 0,
    user_id     BIGINT       NOT NULL,            -- 收件人
    event_type  VARCHAR(64)  NOT NULL,            -- task.created / task.completed
    biz_type    VARCHAR(30),                      -- 跳转定位用（如 PART_RELEASE/ECR）
    biz_id      BIGINT,
    title       VARCHAR(200) NOT NULL,
    content     VARCHAR(1000),
    read_flag   SMALLINT     NOT NULL DEFAULT 0,
    created_at  TIMESTAMP    NOT NULL DEFAULT CURRENT_TIMESTAMP
);
CREATE INDEX idx_notify_inbox ON notify_message (user_id, read_flag, id DESC);
```

### 1.3 双通道摄取（核心决策）

事件总线**默认关闭**（`openforge.event.enabled=false`，MQ 在 compose `rocketmq` profile 后、dev 栈默认不起）。通知若只走 MQ 消费，默认开发态下功能整体失明。故采用仓库既有回退范式（EventPublisher 契约："true=不回退 HTTP"）：

```
workflow emitTask ─┬─ 总线开启 → publish(openforge-task, task.created/.completed)
                   │             → NotifyEventConsumer（auth, 组 openforge-notify）落库（幂等）
                   └─ 总线关闭 → NotifyClient HTTP POST auth 内部接口（X-Internal-Token）落库
```

- **MQ 通道**：auth 内 `NotifyEventConsumer`（骨架复制 ConnectorEventConsumer）订阅 `openforge-task`，消费组 `openforge-notify`——即 B2 设计预留的 notify 组落地。`sys_event_consumed` 幂等 + 租户回填 + FIRST_OFFSET/时间闸门语义同 connector。
- **HTTP 通道**：workflow 侧 `NotifyClient`（模式同 change 模块 `ChangeNotifyClient`）：publish 返回 false 时 POST `/api/v1/internal/notifications`。收件人解析与落库统一在 auth 侧完成，HTTP 通道为 at-most-once 尽力投递（通知属 UX 数据，可接受；MQ 通道 at-least-once）。
- **收件人解析在 auth 侧**：tenant_id 取自收件人 sys_user 记录而非调用方——内部调用无需透传租户，天然免疫越权注入。

### 1.4 MVP 事件→通知映射

| 事件 | 收件人 | 标题模板 |
|---|---|---|
| task.created（USER 指派） | assigneeId | 待办审批：{nodeName} |
| task.created（ROLE 认领） | 该租户持有该角色的用户（fan-out 上限 50） | 待办审批：{nodeName} |
| task.completed | 流程发起人（payload 本批新增 initiatorId 字段） | 审批进展：{nodeName} 已{通过/驳回/取消} |

`task.completed` 原无收件人信息，`WorkflowEngine.emitTask` payload 补 `initiatorId`（向后兼容的追加字段）。其余域事件（part.released 等）payload 无收件人语义，P2 需订阅模型后接入。

### 1.5 API（网关 auth 静态路由追加 `/api/v1/notifications/**`）

| 端点 | 说明 |
|---|---|
| GET `/api/v1/notifications?unreadOnly=&page=&size=` | 我的收件箱（分页，倒序） |
| GET `/api/v1/notifications/unread-count` | 铃铛角标轮询（前端 30s） |
| POST `/api/v1/notifications/{id}/read` | 单条已读（仅本人，他人 404） |
| POST `/api/v1/notifications/read-all` | 全部已读 |
| POST `/api/v1/internal/notifications` | 内部摄取（X-Internal-Token 门禁，workflow HTTP 通道） |

### 1.6 前端

- Header 铃铛（antd Badge + Popover）：最近 8 条、全部已读、"查看全部"入口；30s 轮询 unread-count。
- `/notifications` 通知中心页（概览组新菜单项，`menu:notify` 全角色）。

## 2. 审批委托（workflow 模块）

### 2.1 语义决策：查询期虚拟收件箱（不落库改派）

委托规则生效期间，被委托人的"我的待办"**查询时并集**委托人的 open 任务；办理权限在 act 时校验。优点：规则停用/过期即刻生效、不动存量任务、可回溯。任务表新增 `delegated_from` 列：代办办理时记录原指派人（act 现有逻辑会用办理人覆盖 assignee_id，不补此列则原指派关系丢失）。

### 2.2 数据模型（workflow V4__delegation.sql）

```sql
CREATE TABLE workflow_delegate (
    id           BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    tenant_id    BIGINT      NOT NULL DEFAULT 0,
    principal_id BIGINT      NOT NULL,          -- 委托人（创建者本人，服务端强制）
    agent_id     BIGINT      NOT NULL,          -- 被委托人
    def_key      VARCHAR(64),                   -- NULL=全部流程
    start_time   TIMESTAMP   NOT NULL,
    end_time     TIMESTAMP,                     -- NULL=长期有效
    enabled      SMALLINT    NOT NULL DEFAULT 1,
    remark       VARCHAR(200),
    created_at   TIMESTAMP   NOT NULL DEFAULT CURRENT_TIMESTAMP,
    CONSTRAINT ck_no_self CHECK (principal_id <> agent_id)
);
CREATE INDEX idx_wfd_agent ON workflow_delegate (agent_id, enabled);
CREATE INDEX idx_wfd_principal ON workflow_delegate (principal_id, enabled);

ALTER TABLE workflow_task ADD COLUMN delegated_from BIGINT;  -- 委托代办时的原指派人
```

生效判定：`enabled=1 AND now>=start_time AND (end_time IS NULL OR now<=end_time)`，租户隔离由 controller 上下文注入 tenant_id 保证。

### 2.3 引擎改造点（WorkflowEngine）

- `myTasks(userId)`：原查询 ∪ `assignee_id IN (生效规则的 principal_ids)`；批量回查实例 def_key 做范围过滤；委托来源任务置 `viaDelegation=true`（`@TableField(exist=false)` 瞬态字段，随 JSON 下发前端打标）。
- `act(taskId, userId)`：权限分支追加 `delegatedToMe`（任务 assignee_id 是对 userId 生效规则的 principal）；仅适用 USER 指派任务（ROLE 任务本就可被角色成员认领，不重复委托）。代办办理时 `delegated_from=原assignee` 后再覆盖 assignee_id。
- `emitTask` payload 追加 `initiatorId`（§1.4）。

### 2.4 API（委托属个人操作，登录即可，不走 @RequirePermission；越权由归属校验兜底）

| 端点 | 说明 |
|---|---|
| POST `/api/v1/workflow/delegates` | 创建（principal=当前用户；拒绝自委托/时间倒置） |
| GET `/api/v1/workflow/delegates` | 我发出 + 指给我的规则 |
| DELETE `/api/v1/workflow/delegates/{id}` | 撤销（仅本人规则，他人 404） |

### 2.5 前端

- `/workflow/delegates` 审批委托页（协作组，`menu:delegate`，ADMINS/ENGINEER）：创建表单（被委托人选人/时间范围/流程范围/备注）+ 规则表（我发出/我接收两个 Tab，撤销按钮）。
- 我的待办页：委托来源任务展示"来自委托"Tag（viaDelegation）；`delegatedFrom` 有值的历史任务展示代办标记。

## 3. 回收站（material / doc / drawing 三服务）

### 3.1 范围与端点

软删入口盘点（实现期修正）：全仓仅有 **part（deleteDraft）与 drawing（delete）** 两个真实软删入口——doc 模块无任何删除 API、BOM 无整册删除。故回收站 MVP 收窄为**物料 + 图纸**两域（有真实回收流量的域）；BOM/文档待其删除入口建立后按同构模式接入（本设计模式已验证）。**MVP=列表+恢复**（彻底删除涉及 MinIO 文件 GC，P2）。路径挂各域既有前缀下（模块注册表动态路由按前缀生成，天然覆盖）：

| 服务 | 列表 | 恢复 | 恢复权限（=该域删除权限，删/恢复同权） |
|---|---|---|---|
| material | GET `/api/v1/parts/recycle` | POST `/api/v1/parts/{id}/restore` | part:delete |
| drawing | GET `/api/v1/drawings/recycle` | POST `/api/v1/drawings/{id}/restore` | drawing:manage |

查看权限与各域列表一致（模块内列表端点均未设权限注解，仅认证门槛）。列表与恢复均需绕过 `@TableLogic` 自动过滤 → 各服务新增 `RecycleMapper`（原生 @Select/@Update，显式 `deleted=1` / `SET deleted=0`；租户过滤由 TenantLineInnerInterceptor 统一改写追加，无需手工守卫）。

### 3.2 恢复护栏

- 目标行不存在或未删除 → 404/400；跨租户按不存在应答（R10 语义，租户拦截器自动追加）。
- 唯一键冲突（物料编码/图号已被在册记录占用，`uk_*` 为全行唯一）→ 400 明确报错，不静默改号。
- 恢复审计与删除对称：图纸记 DRW_RESTORE（删除有 DRW_DELETE）；物料域删除本无审计，保持对称不新增。

### 3.3 前端

`/recycle` 回收站页（产品数据组，`menu:recycle`，ADMINS/ENGINEER）：两 Tab（物料/图纸），各列关键字段 + "恢复"按钮（确认弹窗）。

### 6.3 实现期发现（偏离与修正）

1. **回收站范围收窄**（§3 已修正）：盘点发现 doc 模块无任何删除 API、BOM 无整册删除，全仓仅 part/drawing 有真实软删流量——MVP 收窄为两域，BOM/文档待删除入口建立后按同构模式接入。
2. **角色编码已被后续迁移改名**：V2 种子的 `ADMIN` 在现库实为 `ADMINS`（V16 安全加固），通知 ROLE fan-out 与测试种子不得依赖种子编码，改用动态角色编码解析。
3. **同名 H2 库跨测试类共享**：委托规则若不在 @AfterEach 清空，生效规则会泄漏污染其他测试类的权限语义（曾致既有 unauthorizedUserCannotAct 失败）——新增测试一律自带清理。
4. **唯一键即天然防重号**：uk_part_number/uk_drw_number 为含软删行的全行唯一，删除行的编码天然被保留（恢复冲突实际不可达，代码保留为防御）；若未来要释放删号，需改部分唯一索引（PG）并补冲突分支测试。
5. myTasks 查询并集必须收敛在**单个嵌套 and** 内：顶层追加 or() 会让委托人任务绕过 `action IS NULL` 约束（已办任务泄漏进待办）。
6. **mono 同名 mapper bean 冲突（实纱②第三例）**：material/drawing 两域的 `RecycleMapper` 简单类名相同，mono 单 classpath 下 ConflictingBeanDefinitionException——已改名 `PartRecycleMapper`/`DrawingRecycleMapper`。新增域级类一律带域前缀。

### 7.2 EVENT_BUS 真栈首跑暴露的 RocketMQ compose 四处缺口（已修复，docker-compose.yml + deploy/rocketmq/broker.conf + dev-up.sh）
