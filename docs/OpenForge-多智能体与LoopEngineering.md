## 1. 文档说明

| 项 | 说明 |
|----|------|
| 定位 | 在既有 PLM 架构之上，定义一套**多智能体系统（MAS）架构**，覆盖两个平面：<br>① **开发平面**——用 Agent 团队开发/维护 PLM 系统本身；<br>② **运行平面**——把 PLM 内置 AI 能力（数据操作、文档解析等）升级为多智能体协作 |
| 验证方法论 | 两平面统一采用 **Loop Engineering（循环工程）**：任何智能体产出必须进入"生成 → 验证 → 修正"闭环，验证通过才算完成；验证信号结构化回流作为修正依据 |
| 读者 | AI 工程师、后端/前端工程师、架构师、QA |
| 与既有架构的关系 | 复用元数据中心（Agent 的系统地图）、SQL 安全网关（运行时验证器）、知识库（反馈记忆）、CI/CD（循环的基础设施） |

**为何两个平面同构**：开发平面产出代码与配置，运行平面产出 SQL 与解析结果——产物不同，但"生成质量不可信任，必须闭环验证"的工程逻辑相同。同一套 Loop 框架、同一套验证器分级、同一套预算控制，降低体系复杂度。

## 2. 设计理念

### 2.1 多智能体的采用理由

单一大 Agent 处理所有任务存在上下文爆炸、角色冲突、错误共振三大问题。本系统按**领域分治 + 角色分工**拆分智能体：

- 每个 Agent 有**窄而深**的职责（只做一类事），Prompt、工具集、评估标准因此可以高度优化；
- 关键路径上安排**对抗角色**（Generator 与 Verifier 分离、Coder 与 Reviewer 分离），用角色博弈替代单 Agent 自查——自查通过率高但逃逸率高，对抗验证是 Loop Engineering 的质量基石；
- Orchestrator（编排者）负责任务分解与路由，持有全局视图但不亲自执行——避免"既当裁判又当运动员"。

### 2.2 Loop Engineering 五原则

| # | 原则 | 含义 |
|---|------|------|
| 1 | **验证器先行** | 任务下发前先固化"完成标准"（测试用例/Schema/验收断言），Agent 是对着目标函数优化的——没有验证器的循环是空转 |
| 2 | **确定性优先** | 验证手段优先级：编译器/类型检查/单测 > 合同测试/E2E > 规则引擎（SQL 安全网关） > LLM-as-Judge > 人工抽检。能用确定性判定的绝不用模型判定 |
| 3 | **失败即信号** | 验证失败必须产出**结构化修正信号**（错误类别 + 位置 + 原因假设），回流给生成方 Agent，而不是简单的"失败重试" |
| 4 | **预算封顶** | 每个循环声明最大迭代数、Token/时长预算、收敛判据；超限即熔断并升级（换路径或请求人类），禁止无限循环 |
| 5 | **闭环留痕** | 每一轮迭代的输入、产出、验证结果、修正动作全部入库（loop_trace），既是审计依据，也是后续训练/优化的数据资产 |

### 2.3 双平面统一的循环抽象

```
          ┌────────────────────────────────────────────┐
          │              通用 Agent 循环单元             │
          │                                            │
   任务 ─▶│  Plan ─▶ Act ─▶ Verify ─▶ (fail) ─▶ Reflect │─▶ 完成
 + 验收标准 │                │                          │   │     │
          │                ▼ (pass)                    │   │     │
          │              Done                          │◀──┘     │
          │   预算控制器: 迭代上限/Token上限/超时 → 升级    │
          └────────────────────────────────────────────┘
   开发平面: Act=改代码/写配置   Verify=编译+测试+评审
   运行平面: Act=生成SQL/抽取    Verify=SGW校验+DryRun+置信度
```

### 3.1 总览

```
│                     Agent 基础设施（两平面共用）                      │

│  工具网关(git/CI/K8s/DB/PLM API, 全量审计) │ Loop控制器(预算/熔断/升级) │

                │                                    │
┌───────────────┴───────────────┐    ┌───────────────┴────────────────┐
│   开发平面 MAS（Dev Agent Team） │    │     运行平面 MAS（PLM AI 中台）   │

│                               │    │                                │
│ Orchestrator(Dev)             │    │ Router-Agent(意图识别/路由)      │
│ ├ Spec-Agent(需求→验收标准)     │    │ ├ DataOps-MAS(SQL生成执行)      │
│ ├ Coder-Agent×N(按服务域)      │    │ ├ DocParse-MAS(文档解析)        │
│ ├ Reviewer-Agent(代码评审)     │    │ ├ Impact-MAS(变更影响分析)      │
│ ├ Verifier-Agent(测试生成/执行) │    │ ├ Knowledge-Curator(知识策展)   │
│ ├ SecOps-Agent(安全扫描)       │    │ └ Assistant(对话入口/工具调用)   │
│ └ DevOps-Agent(构建部署)       │    │                                │
│ 产物: 代码/测试/低代码元数据制品  │    │ 产物: SQL/解析结果/知识条目/报告   │
│ 验证: 编译/单测/E2E/AI评审      │    │ 验证: SGW/Schema/置信度/引用溯源  │
└───────────────────────────────┘    └────────────────────────────────┘
```

| 既有组件 | 在 MAS 中的角色 |
|----------|----------------|
| 元数据中心（架构文档 5.2） | **Agent 的系统地图**：开发 Agent 读取对象模型/接口元数据获得精确上下文（代替把整个代码库塞进 Prompt）；运行 Agent 读取 Schema 知识做 Text-to-SQL |

| CI/CD + Flyway（架构文档 9.2） | 开发平面 L1/L2 循环的验证基础设施 |
| 灰度发布 / 金丝雀 | L3 系统级循环的"小流量验证"手段 |

## 4. 多智能体系统设计

### 4.1 开发平面：Dev Agent Team

| Agent | 职责 | 关键工具 | 验证闭环对象 |
|-------|------|----------|--------------|
| **Orchestrator(Dev)** | 需求分解、任务路由、进度管理、冲突协调；不写代码 | 任务看板、依赖图 | 任务级完成判据 |
| **Spec-Agent** | 需求 → 技术方案 + **验收标准（测试大纲）**；调用元数据中心核对对象/接口是否存在 | 元数据中心、架构规则库 | 方案评审（人类 + Reviewer） |
| **Coder-Agent ×N** | 按服务域克隆为多个实例：material-coder、workflow-coder、lowcode-coder、frontend-coder、ai-py-coder…；写代码/低代码元数据制品 | 代码库、脚手架、Formily/bpmn Schema 模板 | 编译 + 单测 + Lint |
| **Reviewer-Agent** | 代码评审：架构依赖规则（架构文档 6.3）、安全编码规范、与既有风格一致性 | ArchUnit 报告、静态分析 | 评审清单全绿 |
| **Verifier-Agent** | 测试生成与执行：由 Spec 的验收标准生成单测/E2E；维护测试资产 | 测试框架、测试环境 | 覆盖率门槛 + 用例通过 |
| **SecOps-Agent** | 依赖漏洞扫描、密钥泄露检测、SQL 注入面、AI 出站脱敏检查 | Trivy、Gitleaks、自研规则 | 扫描零高危 |
| **DevOps-Agent** | 构建镜像、部署 DEV/TEST、执行迁移、金丝雀放量 | CI/CD、K8s、Flyway | 部署健康检查 + 冒烟 |
| **Knowledge-Curator** | 从失败 Loop 中提炼"坑与解法"写入项目知识库；维护 Agent 的 few-shot 案例库 | 知识库 API | 人类确认后发布 |

> Coder 按服务域实例化的原因：PLM 微服务边界（架构文档 6.1）天然是上下文边界——每个域的代码规范、数据模型、测试策略差异大，窄上下文使单域代码质量可控，跨域改动由 Orchestrator 拆为多域子任务再汇总。

### 4.2 运行平面：用户侧 AI 功能的 MAS 化

| MAS 组 | 输入 | 成员协作 | 输出（均经 Loop 验证） |
|--------|------|----------|------------------------|
| **DataOps-MAS** | 自然语言数据指令 | Router → Planner(选通道API/SQL) → SQL-Gen → **SGW-Verifier** → Executor → Reporter | 查询结果/写操作+回执 |
| **DocParse-MAS** | 文档文件 | Dispatcher(格式分流) → Extractor(OCR/表格/CAD) → Schema-Validator(JSON Schema+置信度) → Corrector(低置信度字段定向重读原文) → Human-Queue | 结构化属性+摘要 |
| **Impact-MAS** | 变更请求 | Graph-Walker(图数据库确定性影响面) → Evidence-Retriever(RAG 历史案例) → Synthesizer(综合报告) → Fact-Checker(引用溯源核对) | 影响分析报告 |
| **Knowledge-Curator-MAS** | 业务事件/反馈 | Collector → Summarizer → Dedup-Agent(向量查重) → Quality-Scorer → (低分→)Human-Review | 知识条目 |
| **BOM-Clean-MAS** | Excel BOM | Header-Mapper → Entity-Resolver(编码/规则/向量三级匹配) → Anomaly-Detector → Report-Gen | 清洗报告+合并建议 |

设计约定：

- 每个 MAS 内部 **Generator 与 Verifier 必须是不同 Agent 实例**（不同 Prompt/模型均可），防止自我确认偏误；
- Router-Agent 是用户唯一入口，持有会话与用户身份，**所有下游 Agent 继承该身份做权限校验**（权限 = 用户权限 ∩ Agent 权限，架构文档 10 章）；
- MAS 间可组合：Assistant 可把任务委派给 DataOps-MAS 或 Impact-MAS，形成两级编排（MAS of MAS），但编排深度限两层，防止失控链路。

### 4.3 通信与状态

```
共享工作区(Blackboard):  git分支(代码) / 任务看板(状态) / 制品库(元数据包) / 知识库(记忆)
消息机制:                事件总线(rocketmq, 运行平面) / 任务队列(开发平面)
Agent间消息:             结构化信封 {task_id, sender, receiver, intent, payload, deadline, budget}
状态机:                  任务 Task: pending→planning→executing→verifying→blocked→done/failed/escalated
```

不采用 Agent 间自由对话（聊天式协商）：所有协作经过 Orchestrator 路由 + 黑板共享状态，保证**可追溯、可重放**——这是工程系统与实验性 MAS 的关键区别。

## 5. Loop Engineering 验证体系（核心）

### 5.1 四层循环模型

```
┌─ L3 系统演化环 ──────────────────────────────────────────────────────┐
│  发布 → 生产遥测(指标/用户反馈/AI采纳率) → 知识库沉淀 → 下一迭代规划     │
│  周期: 周/月级 ｜ 验证: 灰度指标+回滚 ｜ 参与者: 全体+人类              │
│ ┌─ L2 特性交付环 ─────────────────────────────────────────────────┐  │
│ │  Spec(含验收标准) → 实现(多Agent) → 集成/E2E验证 → 评审 → 合并     │  │
│ │  周期: 天级 ｜ 验证: E2E+AI评审+人审门 ｜ 产出: 可发布制品          │  │
│ │ ┌─ L1 任务修复环 ────────────────────────────────────────────┐  │  │
│ │ │  生成 → 确定性验证(编译/单测/SGW/Schema) → 失败→修正信号→重生成 │  │  │
│ │ │  周期: 分钟级 ｜ 迭代上限: 默认5次 ｜ 超限→升级              │  │  │
│ │ │ ┌─ L0 Agent内核环 ────────────────────────────────────┐   │  │  │
│ │ │ │  Think → Act(工具调用) → Observe(结果) → Reflect     │   │  │  │
│ │ │ │  单步循环, 由Agent Runtime(LangGraph)承载             │   │  │  │
│ │ │ └──────────────────────────────────────────────────────┘   │  │  │
│ │ └────────────────────────────────────────────────────────────┘  │  │
│ └────────────────────────────────────────────────────────────────┘  │
└────────────────────────────────────────────────────────────────────┘
```

| 层 | 触发 | 通过标准（门禁） | 失败去向 |
|----|------|------------------|----------|
| L0 | 每次 Agent 推理步 | 工具调用成功、观察可解析 | 步内重试 ≤2 次 |
| L1 | 每个任务产出 | 编译零错 / 单测全绿 / SGW 五层过 / Schema 校验过 / 置信度 ≥ 阈值 | 结构化修正信号回生成方，≤5 轮 |
| L2 | 每个特性完成 | E2E 通过 + 覆盖率 ≥ 门槛 + 评审清单全绿 + 人工批准 | 打回 Spec 重对齐 |
| L3 | 每次发布后 | 灰度期错误率/采纳率达标 | 自动回滚 + 复盘入知识库 |

**环间规则**：内环未绿不得进外环（单测不绿不上集成）；外环失败回流时必须携带外环验证器的具体失败证据，供内环定位（禁止裸"重做一遍"）。

### 5.2 验证器分级（Verifier Hierarchy）

| 级 | 验证器 | 判定方式 | 应用 |
|----|--------|----------|------|
| V1 | 编译器/类型检查/Lint/JSON Schema | 完全确定 | 代码、配置、抽取结果 |
| V2 | 单元测试/合同测试/规则引擎（SQL 安全网关） | 完全确定（预置规则） | 代码行为、SQL 合法性权限 |
| V3 | 集成/E2E/沙箱试跑/Dry-run | 确定但依赖环境 | 服务交互、流程配置、SQL 写操作 |
| V4 | LLM-as-Judge（Rubric 评审）/ 引用溯源核对 | 概率性，需抽样校准 | 文本报告、代码评审初筛、RAG 答案引用 |
| V5 | 人工抽检/审批门 | 人类 | 发布、高风险写、低置信度字段 |
| V2+ | 性能自检清单（PR 模板合并门） | 完全确定（画像文档 §5 条目可溯源） | 资源上界/连接池/聚合下推/调度格式/环境画像核对 |

规则：**V4 只能做初筛与排序，不能做最终放行**；性能维度的清单验证器（V2+）由 v1.3.0 后本地全量拉起闪退事故催生，条目与基线见《OpenForge-性能与容量画像》§5，PR 模板为强制合并门；凡 V4 判"过"的产物按比例进 V5 抽检，抽检逃逸率反哺 Rubric 校准（这本身又是一个反馈环）。

### 5.3 预算与熔断（Loop 控制器）

每个循环单元创建时声明预算，由 Loop 控制器统一执行：

```yaml
loop_policy:
  max_iterations: 5          # L1 最大迭代
  token_budget: 200_000      # 单任务 Token 上限
  wall_clock: 30m            # 墙钟超时
  convergence: "tests_green && review_clean"   # 收敛判据
  on_exhaust:                # 预算耗尽 → 分级升级
    - retry_with_new_path    # ① 换策略重试(换Prompt版本/换模型/换分解方案)
    - split_task             # ② 任务再拆分
    - escalate_human         # ③ 升级人类(携带全部loop_trace)
```

### 5.4 修正信号协议（失败即信号原则的落地）

验证器输出统一结构，供生成方定向修复：

```
FixSignal {
  verifier:   "sql_safety_gateway"          # 谁判定失败
  category:   "PERMISSION | SYNTAX | RULE | SCHEMA | CONFIDENCE | TEST | LINT"
  location:   "clause:where / file:xx.cs:120 / field:外径"
  evidence:   "表part不在白名单矩阵中(insert)"  # 原始证据
  hypothesis: "用户意图可能为查询而非写入"       # 修正方向建议
  retry_hint: "改走API通道: POST /api/v1/parts" # 可执行的重试建议
}
```

## 6. 开发时应用：用 MAS 开发 PLM

### 6.1 开发流水线（L2 特性交付环的实例化）

```
需求 Issue ──▶ Orchestrator(Dev)
 ① 派发 Spec-Agent ─▶ 技术方案+验收标准+测试大纲 ─▶ 人类确认(Spec门)
 ② 按域拆任务 ─▶ Coder-Agent×N 并行(各自feature分支)
      每个Coder内嵌L1环: 生成→编译→单测→lint→修复(FixSignal回流)→收敛
 ③ Verifier-Agent ─▶ 由验收标准生成E2E/合同测试 ─▶ 测试环境执行
      失败→FixSignal→对应Coder修复 (≤5轮) ; 超限→escalate_human
 ④ Reviewer-Agent + SecOps-Agent 并行评审/扫描
      V4初筛(评审清单)→人类review把关(merge门)
 ⑤ DevOps-Agent ─▶ 合并→构建→DEV部署→冒烟 ─▶ TEST回归 ─▶ 待发布队列
 ⑥ Knowledge-Curator ─▶ 本次迭代的坑与解法入知识库(供后续Agent检索)
```

### 6.2 与低代码平台的协同（本系统独有的开发形态）

PLM 的元数据驱动架构让 Agent 拥有两条开发路径，**优先用配置路径**：

| 路径 | Agent 动作 | 验证手段 |
|------|-----------|----------|
| **低代码路径（默认）** | 调用元数据中心 API 生成对象模型/表单/流程/规则制品 | 沙箱预览试跑（开发文档 6.5）+ 兼容性检查 + 影响分析——**无需写代码即可完整验证** |
| 代码路径 | 生成 Java/Python/TS 代码（核心域逻辑、新连接器、组件） | 编译+单测+E2E 全套 |

低代码路径使 Agent 的"修改影响面"被平台元数据依赖图天然约束（架构文档 5.2），大幅降低 Agent 改坏系统的风险——**平台为 Agent 提供了结构化的安全围栏，这是通用编码 Agent 不具备的优势**。

### 6.3 Agent 的上下文供给（防上下文爆炸）

- 代码上下文：不塞全库；由元数据中心提供"该任务涉及的对象模型 + 接口契约 + 相关表结构"，加上知识库检索的"历史相似实现案例"（Top-3）；
- 规范上下文：架构依赖规则（6.3）、编码规范、安全清单以 Checklist 形式注入 Reviewer 而非 Coder（角色分工）；
- 项目记忆：Knowledge-Curator 维护的"本项目坑库"按任务标签召回。

## 7. 运行时应用：PLM 功能的多智能体化升级

### 7.1 DataOps-MAS（升级开发文档 4.7 的执行内核）

```
用户: "帮我新增一个45#钢的法兰盘，外径120"
 Router-Agent ── 意图识别(写操作) + 身份上下文注入
      │
 Planner-Agent ── 检索schema知识 → 通道决策(API优先) → 操作计划
      │            └─(L1环) 计划自检: 字段齐全?分类正确? ──否→补全重规划
 SQL-Gen / API-Composer-Agent ── 产出SQL或API报文
      │
 SGW-Verifier(确定性V2/V3) ── 五层校验 + Dry-run
      │ 失败 → FixSignal{category: RULE|PERMISSION...} → 回SGen修正(≤3轮)
      │ 超限 → 降级: 生成"人工操作指引"返回用户
 Executor-Agent ── 事务执行(写: L2/L3确认门在前) + 反向SQL留存
      │
 Reporter-Agent ── 结果+SQL折叠面板+溯源 ── 用户
      └─ 事后: 执行成败/用户修正 → 知识库SQL纠错回流(开发文档5.6(5))
```

相对单 Agent 的增益：Planner 的通道决策、SGW 的确定性判定、Reporter 的溯源组装各自独立优化；SQL-Gen 的修正只针对 FixSignal 指出的类别，收敛轮次平均下降（目标 ≤2 轮）。

### 7.2 DocParse-MAS 的置信度回路

```
Dispatcher(PDF/Office/CAD分流)
 → Extractor(OCR+版面) → V1: JSON Schema校验
      │ 字段级置信度 < 0.85
 Corrector-Agent: 只对低置信字段, 带页码/坐标定位重读原文局部(避免全文重跑)
      │ 两次仍低 → Human-Queue(校对界面, 原文高亮对照)
 → 属性回填 + 摘要 + 知识入库
```

人工校对的每一次修正写回 `ai_job`，成为 Corrector 的 few-shot 素材与后续微调数据（自适应闭环）。

### 7.3 Impact-MAS 的双通道互证

- Graph-Walker 的确定性影响面（BOM 反查/关联文档/在途变更）**不需要 Loop**——它是数据库查询；
- Synthesizer 生成的分析报告进入 **Fact-Checker 回路**：报告中每一条"历史案例引用"必须能在知识库中定位到源条目（引用溯源核对，V4），未通过的引用剔除或降级标注；
- 报告最终附"确定性数据 + 推理性内容"分区，用户可区分事实与推断。

## 8. 关键功能的验证回路详设

| 功能 | 生成方 | 验证器（按序） | 修正策略 | 升级点 |
|------|--------|----------------|----------|--------|
| **SQL 生成** | SQL-Gen-Agent | V2 SGW 五层 → V3 Dry-run 回滚试跑 | FixSignal 类别定向（语法→重写；权限→换通道；规则→改走 API） | 3 轮未收敛→人工指引 |
| **BOM 清洗** | Entity-Resolver | V2 规则（编码格式/单位/数量域）→ V4 相似度裁决 | 模糊匹配阈值自适应下调，候选扩到 Top-8 | 冲突对→人工裁决队列 |
| **文档解析** | Extractor | V1 Schema → 字段置信度 | Corrector 局部重读 | 两次低置信→人工校对 |
| **流程配置** | Coder/低代码路径 | V1 Schema → V3 沙箱试跑+影响分析 | 节点级 diff 修正 | 兼容性冲突→人工 |
| **代码开发** | Coder-Agent | V1 编译/lint → V2 单测 → V3 E2E | 测试失败堆栈→定向修复 | 5 轮→换路径→人类 |
| **知识入库** | Summarizer | 向量查重(V2 近似) → Quality-Scorer(V4) | 重写摘要/合并源 | 低分→人工审核 |
| **AI 评审初筛** | Reviewer-Agent | Rubric 清单 | 逐条整改 | 人类 review 终审 |

## 9. Agent 基础设施

### 9.1 组件构成

| 组件 | 职责 | 技术落点 |
|------|------|----------|
| Agent Runtime | Agent 编排、状态机、L0 循环承载 | LangGraph（两平面同一套 runtime） |
| Loop 控制器 | 预算声明/迭代计数/收敛判据/熔断升级 | Runtime 内中间件 + 独立策略服务 |
| 工具网关 | 全部工具调用的唯一出口：鉴权、审计、限速、沙箱路由 | 自研（复用 SQL 安全网关的校验框架扩展为 Tool Safety Gateway） |
| 上下文服务 | 元数据检索、知识 RAG、项目记忆召回 | 元数据中心 + 知识库（现有组件） |
| 沙箱 | 代码执行、Dry-run、流程试跑 | K8s Job / 事务回滚 / 流程沙箱（现有） |
| loop_trace 存储 | 每轮迭代的输入/产出/验证/FixSignal 全留痕 | PostgreSQL（可回放、可训练） |
| Agent 可观测 | 追踪（跨 Agent 链）、指标、Token 成本归集 | OpenTelemetry → 既有 SkyWalking/Prometheus 栈 |

### 9.2 安全模型（承继既有原则）

- **权限合成不变**：Agent 有效权限 = 触发用户权限 ∩ Agent 角色权限 ∩ 工具白名单（架构文档 10 章）；开发平面触发"用户"= 提交任务的工程师，Agent 无法超越该工程师的 Git/系统权限；
- **写操作分级不变**：L1~L4 与确认门（开发文档 4.7.3）原样适用于 Executor-Agent；
- 开发平面独有：Agent 不得自行合并主干/触发生产部署/修改权限配置——这三个动作永久人类门禁；
- 所有 Agent 产出的代码与配置打 `author=agent:<id>` 标签，与人类提交在 Git/审计中可区分。

## 10. 人机协作与门禁

| 门禁 | 位置 | 人类动作 | 旁路规则 |
|------|------|----------|----------|
| Spec 门 | L2 环起点 | 确认方案与验收标准 | 纯 bug 修复类可免（验收标准由 Issue 模板预置） |
| Merge 门 | L2 环终点 | 代码评审批准 | 测试全绿+低风险变更可配置"快速通道"（抽样事后审） |
| Release 门 | L3 环 | 发布批准 | 仅 DEV/TEST 环境免 |
| 写操作确认门 | 运行平面 L2/L3 写 | 确认卡片 | L1 只读免确认 |
| 升级处理 | Loop 熔断后 | 处理带完整 loop_trace 的工单 | — |

人类处理升级工单后的动作（采纳/改写/否决）回写知识库——**人类的每一次干预都变成 Agent 的训练素材**，干预频率本身是体系健康度的核心指标（见 11）。

## 11. 指标体系

| 类别 | 指标 | 目标（首年） |
|------|------|--------------|
| 收敛 | L1 循环收敛率（预算内完成） | ≥ 85% |
| 质量 | 首轮通过率（Verify 一次过） | ≥ 50% 并持续上升 |
| 质量 | 逃逸率（Agent 判过但人工/生产发现问题） | ≤ 3% |
| 效率 | 平均迭代轮次 | ≤ 2 |
| 成本 | 单任务 Token 成本 / 人工干预次数 | 环比下降 |
| 采纳 | 运行平面 AI 建议采纳率（用户点"采纳"比例） | ≥ 60% |
| 干预 | 升级工单占任务比 | ≤ 15% 并递减 |

指标看板按 Agent / MAS 组 / 循环层级三维度切分，异常（如某 Coder 逃逸率突增）自动触发该 Agent 的 Prompt/模型版本回滚。

## 12. 实施路线与风险

### 12.1 路线（对应架构文档 13 章阶段）

| 阶段 | 内容 |
|------|------|
| MAS-1（随架构阶段一） | 基础设施先行：Agent Runtime + 工具网关 + loop_trace + 单 Agent 接入 CI（Coder 的 L1 环）；运行平面先改造 DocParse-MAS（回路简单、风险低） |
| MAS-2（随阶段二） | Dev Team 全角色上线（Spec/Reviewer/Verifier/SecOps）；DataOps-MAS 上线（SGW 作为确定性验证器复用）；低代码路径开发流程打通 |
| MAS-3（随阶段三） | Impact-MAS、Knowledge-Curator-MAS；L3 系统环接入灰度遥测；loop_trace 开始反哺 Prompt/微调优化 |
| MAS-4（随阶段四） | Agent 生态治理：模型版本 A/B、Agent 市场（内部）、指标驱动的自动优化（AutoPrompt 迭代环） |

### 12.2 风险与对策

| 风险 | 对策 |
|------|------|
| Agent 间错误传播（上游错误污染下游） | 黑板上的产物必须带验证状态标签；未过 V1/V2 的产物不可被下游引用 |
| Loop 空转烧钱 | 预算硬顶 + 熔断升级 + 语义缓存；收敛判据必须机器可判 |
| LLM-as-Judge 与生成方同源偏置 | Judge 使用不同模型家族；V4 永远不终审 |
| Agent 权限被滥用（提示注入诱导越权） | 工具网关白名单 + 权限合成交集原则 + 出入站脱敏 + 全量审计；提示注入测试纳入 SecOps-Agent 扫描项 |
| 人类过度依赖导致技能退化 | 逃逸率与抽检制度强制保留人类深度参与点（Spec 门/Merge 门） |
| loop_trace 隐私（含用户指令与数据） | trace 脱敏归档、分级保留期、训练用途需租户授权 |
